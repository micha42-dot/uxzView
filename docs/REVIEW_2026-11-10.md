## Findings and corrections

### Duplicate results could still become macOS sheets

The result dialog requested ApplicationModal but then called `QDialog::open()`.
Qt changes that to WindowModal; Qt 6.8 also reparents it as a sheet on macOS.
Four new checks failed against the unchanged implementation. The
[Qt 6.8.3 implementation](https://github.com/qt/qtbase/blob/v6.8.3/src/widgets/dialogs/qdialog.cpp)
confirms the platform behavior.

The dialog now uses `show()` with its explicit ApplicationModal setting. Its
completion signal records a finished flag before display, so closing from a
native Show handler cannot strand a subsequently started event loop. The existing
worker join, delayed progress and user cancellation behavior remain intact.

### Three named tests actually selected the same action

The parent still sent German button text while the subprocess expected ASCII
action IDs. Unknown IDs silently selected the similar-image action, so index and
exact-duplicate checks were not exercising their advertised paths. The parent now
sends the ID; invalid IDs are rejected. The subprocess reports its actual action,
result title, modality and window type, all of which the parent verifies.

### The progress-window race was not forced

Empty catalog work normally finished before the 200 ms progress delay, leaving
the Show-event probe unused. A test-only pool barrier now holds the job until the
progress window's Show event. Every case requires that probe to have run. Two
additional cases close duplicate results synchronously during Show. Subprocesses
inherit the selected Qt platform, enabling actual native Windows checks as well
as the ordinary offscreen CI runs. No product delay or larger timeout was added.
