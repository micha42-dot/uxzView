# Cache and metadata state review — 27 October 2026

This review builds on the unpublished changes described in the preceding CI
and performance reports. It examines cache invalidation across worker
completion, retained image metadata, saved-document/Undo metadata flags,
cancellation/lifetime boundaries, file revisions, and Windows/native/portable checks. It does not claim
an exhaustive security audit or a successful Linux/macOS run.

## Confirmed: cache clear can be undone by an older worker

`ImageLoadCache::read` released its mutex while decoding and unconditionally
inserted the result when the worker returned. A clear followed by a new read
could therefore be overwritten by an earlier read finishing last.

The regression pauses a codec with semaphores after its first read starts,
clears the cache, completes a new read, then releases the older read. In the
original implementation the next cache lookup returns the older red image
instead of the newer blue image. It does not depend on scheduling delays,
filesystem timestamp resolution or external edits.

Both the document and thumbnail paths now capture a cache epoch under the
existing mutex. `clear()` advances that epoch while clearing the caches. A
completed operation inserts only if its captured epoch is still current.
Work already running may finish and return to its original caller; clearing
does not become a new cancellation or UI-error mechanism. UI request
generations/lifetime guards still decide which results are displayed.

## Confirmed: pixel-only charging misses retained payloads

Document/thumbnail entries were charged only `QImage::sizeInBytes()`. A tiny
image with a 600,000-character comment, document text, metadata value or large
ICC profile was cached under a 1 MiB budget even though its auxiliary payload
alone exceeds that budget. A real PNG demonstrates the same issue for scaled
thumbnails. Small metadata controls still cache correctly.

The shared private cost helpers now include pixel buffers, image comments,
document text, source/key/warning strings, ICC bytes and native metadata
estimates. QString capacities and per-entry overhead are included; implicit
sharing can make charges conservative. No text, image samples or profiles are
removed or modified to make an entry fit.

`readMetadata` estimates native tag/value/data-area storage during its existing
collection pass. EXIF data areas include embedded thumbnails. The original
whole image-file length is not treated as metadata cost: a large JPEG with
ordinary EXIF should retain useful caching. Accounting failures in Exiv2 fall
back conservatively without discarding otherwise readable metadata. The
legacy/new pointer and API compatibility paths remain supported; the optional
data-area query uses C++20 compile-time availability checking.

An unsupported QColorSpace can still retain the original ICC bytes. Those are
charged too, matching the
[Qt 6.8.3 implementation](https://github.com/qt/qtbase/blob/v6.8.3/src/gui/painting/qcolorspace.cpp).
Regression cases cover valid and unsupported profiles.

Arithmetic saturates one byte above the largest configurable 512 MiB budget,
so an oversized estimate cannot wrap into a small/negative cost or be accepted
at that maximum. A synthetic maximum-integer native estimate verifies the
boundary without allocating a huge buffer. The existing 96 MiB pixel-buffer
admission ceiling remains; the complete entry cost is charged to the configured
cache budget. Costs are calculated outside the cache mutex, only on insertions,
and skipped when the corresponding cache was disabled at request start.

## Confirmed: a successful save can invent metadata presence

`MainWindow::saveImage` marked a saved document and its Undo history as having
source metadata whenever a metadata object existed and the format supported
metadata. A valid empty Exiv2 result also has an object. Saving a plain PNG
therefore changed `sourceHasExif` to true although rereading the saved file
reports false. Subsequent exports to a format without metadata support can
produce a spurious EXIF/IPTC/XMP-loss warning.

The existing Save-as/Undo regression now compares the active flag and loss
report with a fresh decode of the actual saved target, and checks the source
flag again after Undo. The original code fails that comparison (two passes,
one failure including setup/cleanup). Evidence:
`build/cache-review-save-state-before.txt`.

The completed transaction now determines whether it actually wrote native
metadata from the output metadata containers, EXIF/IPTC/XMP presence flags and
the chosen format. That same source fact is installed in the document and its
Undo history, together with the destination/revision already retained there.
It does not decode the image again as part of saving. Selection exports leave
the active source state untouched. Legitimate alpha/depth/profile/metadata loss
checks remain in place; the regression compares the full BMP loss report too.

## Limits retained

Cache budgets are estimates for retained cache entries, not a process-RAM cap.
Active images, display images, undo, UI pixmaps, decoder allocations, parsing,
allocator overhead and simultaneous work are additional consumers. Shared
metadata can be charged more than once. The accounting does not bound memory
used while parsing a file before a cache entry exists.

Native file revision keys are not content hashes. Coarse timestamps or a
filesystem unable to expose a changed revision can still hide rapid same-size
external rewrites; explicit clears now have a stronger cache-lifetime boundary.
File checks/mutations remain non-atomic against other processes. Third-party
decoders can continue until their reads return after cooperative cancellation.
