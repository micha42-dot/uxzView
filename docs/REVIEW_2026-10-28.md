# Critical review — 28 October 2026

This pass concentrates on scaling and failure boundaries rather than adding
viewer features or changing its decoder/cache/colour-management paths.

## Corrected findings

- The batch dialog stacked two large views inside another scroll area. Configuration
  and results now occupy separate tabs; actual list views retain their own scrollbars.
  Files, chain and output options now have one full-width vertical reading order;
  action buttons use equal grid columns and the destination retains its gap.
- Each result snapshot allocated four QTableWidgetItems per file and eagerly
  formatted every path/status. A read-only table model retains Qt-shared results
  and formats requested cells. Step editing lives in its own module.
- Input additions repeatedly searched the entire list. A temporary set makes exact
  deduplication linear on average. Routine validation no longer copies every input.
- CSV construction retained the entire report and ran on the GUI thread after
  conversion. It now streams in bounded chunks on the worker, with independent
  report errors and cleanup of partially written files.
- A fully skipped batch still loaded watermark resources and constructed workers.
  It now returns existing per-file results before that work; actual thread count
  is limited by eligible files.
- Non-standard decoder exceptions escaped the per-file std::exception handler in
  std::thread, leading to terminate. A final handler records a file failure instead.

## Remaining priorities

   Keep the extraction roadmap in ARCHITECTURE.md; moving methods between source

## Linux optional-module packaging

The supplied Linux log proves that the app and image probe start but Python's
installed-module check cannot load ixextensions.so: libQt6Network.so.6 is absent
from its loader context. Our deployment list passed installed modules, whose
RUNPATH had already become $ORIGIN/.. before SDK-only dependencies were copied.

Qt 6.8.3's generic deployment forwards ADDITIONAL_MODULES to CMake's recursive
ELF dependency scanner. That scanner searches ELF RUNPATH/RPATH and ldconfig paths;
CMake does not use the shell's LD_LIBRARY_PATH as a replacement for those paths.
The build app still had an SDK RUNPATH, so its dependencies could deploy while
Network, referenced only by the lazy optional manager, was unresolved. Qt 6.8.3
retains unresolved names without failing this generic deployment call.

`cmake/NativeDeployment.cmake` now supplies build module paths on Linux, retaining
SDK resolution during scanning. Installed modules keep their relocatable RUNPATH.
macOS bundle paths and Windows installed paths retain their previous behavior;
Network is not linked into the base viewer merely to force deployment.

Sources: [Qt 6.8.3 deploy support](https://github.com/qt/qtbase/blob/v6.8.3/src/corelib/Qt6CoreDeploySupport.cmake),
[CMake ELF scanner](https://github.com/Kitware/CMake/blob/v3.28.3/Source/cmBinUtilsLinuxELFLinker.cxx).

The Linux CI job now runs `tests/check_linux_module_deployment.py`. Its small
C fixture shares the real deployment-path helper, first reproduces the missing
installed-module dependency, then deploys via the build module, hides its mock SDK,
and loads the staged module both before and after moving the runtime directory.
It needs no Qt, network access or root privileges. The existing installed-app
module check is unchanged and still rejects missing dependencies/exports.

This Windows host has no registered WSL distribution. The ELF fixture and final
Qt Linux package therefore need confirmation in the next native GitHub run;
Windows tests are not presented as proof of Linux runtime success.

The final portable Windows runtime passes all **356 Qt cases** without SDK paths,
including the required RAW fixtures, real OCR/QR executables, all five language
models and relocated profile/tools startup. All imports resolve in 135 PE modules;
seven existing bundled tool packs are preserved. Windows/source ZIPs are generated
from this tree and checked byte for byte; the native Linux Qt package and the new
ELF regression remain for the next GitHub run.

## Interrupted journal operations and batch progress

`core/file_journal_recovery.cpp` reconciles pending forward/Undo intent under the
same process/interprocess locks as normal journal operations. It checks regular
files, SHA-256 content and absence of conflicting paths. A missing replacement
target can be restored from its verified internal backup. Changed files, unknown
states and legacy Undo records without a recorded discard path remain for manual
inspection; recovery never guesses a trash filename or overwrites an occupied path.

Undo now records its discard path before moving bytes. Retrying an interrupted
Undo resolves that same entry instead of silently undoing an older operation.
A failed replacement Undo whose rollback also fails retains its pending intent.
A final record-write error explicitly says that the file already changed.
The journal offers Check interrupted operations, running its hashing off the GUI
thread. Opening images, normal startup and reading history do not trigger repair
or a scan of image contents. Ambiguous records are retained and reported.

The dedicated headless journal suite injects final persistence failures, covers
copy/move/delete/create/replace and interrupted Undo/backup restoration, and checks
changed targets/backups, ambiguous duplicate sources, old records, out-of-journal
backup paths, held locks and retry idempotence. It is included in CTest and the
portable-runtime verifier. These are injected failure states, not power-cut tests;
QSaveFile plus intent records do not establish fsync-level transaction durability.
Filesystem mutations by unrelated processes remain outside the journal lock.

`ui/batch_progress.h` coalesces worker completions into a per-run monotonic counter
with at most one queued GUI notification in addition to a running delivery. A
100,000-completion burst before delivery schedules one event; late/out-of-order
completions do not move the counter backward. A new run has a new mailbox, so old
plan/progress deliveries cannot replace its UI state. This bounds presentation
work; it is not a measured improvement in decoder or conversion throughput.

## Panorama navigation: automatic fit with locked zoom

A new four-row regression reproduces two failures before the fix: Window and
LargeOnly each become Original on the next image if lockZoom is enabled. The
successor inherits a numeric factor computed for the previous image, creating
real scroll ranges which consume navigation input. The unlocked controls pass.
The user subsequently confirmed that zoom locking was disabled, so that first
finding does not by itself explain the reported configuration.

`MainWindow::installDocument` now retains the numeric factor only for an active
manual/Original view. Automatic fit remains automatic and is recalculated per
image, with fullscreen's existing policy taking precedence. The regression uses
20,003-pixel-wide panoramas and real keyboard/wheel folder navigation, checks
zero scroll ranges/full bounds with preview strips and window resizing, and
checks that deliberately locked 200% manual zoom still works. A fresh-window
check covers a saved zoom lock on the first image. The validator runs these
cases through Windows' native plugin at 100/125/150/200 percent scaling.

### Independent fit-policy failures without zoom locking

Generated JPEG fixtures at the supplied dimensions (3331 × 2244 and 2594 × 3486)
reproduce two failed fullscreen-settings cases: changing the window policy to
LargeOnly while fullscreen leaves the saved return policy at Original. On exit,
images therefore have real scroll ranges despite the Settings value. Source review also identifies a close-time write which lets an older
Original-mode window replace a newer LargeOnly preference. A separate regression
uses two loaded windows and checks that closing the older one preserves the
newest preference. These are state-policy errors, rather than
proof of a floating-point error in whole-image fitting. Original image files
were not provided; dimensions alone cannot establish their metadata/decoder path.

Fit is now persisted only on explicit commands/Settings acceptance. The fullscreen
return policy receives window-fit changes; accepting Settings also reconciles a
stale window's local policy with the displayed global value. Deliberate manual
zoom remains intact when its browsing policy still matches. The fullscreen-close
regression now selects Original through the real user command, which persists it
immediately, rather than relying on a private view mutation during test setup.

## Optional ZIP/CBZ image reader

Added a separate Qt image-format module backed by the KArchive library already
present in the Windows runtime. It exposes archives through existing open filters,
format management, previews and page navigation; single-page export keeps the
archive unchanged. The handler owns one archive and one embedded image decoder.
It never extracts files and does not recursively open nested archives. Page names
are sorted naturally with a stable case-sensitive tie break.

A bounded central-directory check precedes KZip tree allocation; entry buffers
and image geometry have separate limits. The explicitly limited ZIP subset is
documented in FORMAT_COMPATIBILITY.md. An input-device adapter prevents KZip from
closing Qt's borrowed QFile while probing an invalid container. Both successful
page/UI cases and ten invalid-container cases pass. No RAR/CBR, PDF or JPEG XR
backend was added. KArchive remains optional; native CI currently omits it.

Evidence: `build/archive-validation-summary.json` (all 45 Python tests and all
six CTest suites); 379 Qt cases pass without skips. `build/archive-native.txt`
passes all 14 targeted native cases, including setup/cleanup. The portable
runtime passes the same 379 Qt cases and real QR/OCR/relocated-profile checks
without SDK paths (`build/archive-portable.log`). `build/archive-disabled-configure.log`
confirms a fresh disabled configuration removes a deliberately stale generated
plugin. `build/archive-viewer-imports.log` confirms no direct KArchive import in
the app. The new Windows plugin is 104,510 bytes; no additional third-party DLL
was added. This is not a benchmark proving zero startup cost. The prior full
